# ADR-0002：采用零删除、追加事实与前向修复策略

- 状态：Accepted
- 决策日期：2026-08-02
- 决策所有者：LibraMAS 项目
- 适用范围：源码、文件、MySQL、Chroma、Neo4j、Docker 持久化、测试/演示/实验数据
- 关联文档：[安全与零删除政策](../SAFETY_POLICY.md)、[删除操作申请模板](../DELETE_REQUEST_TEMPLATE.md)

## 背景

LibraMAS 是面向智慧图书馆推荐研究的多智能体原型。系统需要同时满足：

1. 推荐过程、画像演化、Agent 协作和实验结果可复现、可解释、可审计；
2. MySQL 事实层与 Chroma、Neo4j 派生索引可独立演化和降级；
3. 失败场景不会通过清空、重置或重新初始化掩盖问题；
4. 用户明确要求禁止删除文件或任何数据库数据，任何删除前必须先提交详细报告。

传统的“重置开发库”“测试后销毁”“原地重建索引”“迁移失败后降级”等做法会破坏证据链，也会使论文指标难以复算。多智能体系统中的 LLM 输出还具有不确定性，因此 Agent 不能直接拥有破坏性基础设施能力。

## 决策

项目采用零删除与 append-first 策略：默认永不删除既有文件、事实数据、派生索引、持久卷和实验证据；业务更正使用追加版本、补偿事件、失效状态和查询过滤；失败通过前向修复恢复。

任何无法证明零删除的操作均 fail closed。确实出现删除需求时，当前工作立即暂停，按删除申请模板向用户提交精确目标、影响、替代方案、备份、恢复演练、dry-run 和拟执行动作。只有用户对未变化的申请编号作出明确、一次性批准后，才可在该申请边界内重新评估执行。

### 1. 事实与版本模型

- MySQL 是唯一业务事实源。行为、反馈、画像变更、配置、策略决策和任务状态都保留可追溯历史。
- 已提交事实不原地改写或移除。撤回和纠错通过新事件表达，投影根据事件顺序计算当前视图。
- 允许更新的仅是明确白名单的技术状态字段，例如租约、重试状态或活动指针；每次更新必须有版本检查并追加状态迁移日志。
- Chroma 和 Neo4j 是派生索引，任何数据都必须能由 MySQL 事实、版本化输入和确定性构建配置重建。
- 文件、Fixture、数据集和实验结果按版本或 `run_id` 创建，不覆盖同名产物。

### 2. 迁移策略

Schema 只允许 expand-only 演化：创建新表、增加 nullable 列、新索引和新约束。外键采用限制删除的引用规则。已执行迁移不可修改，迁移失败或设计变更通过新的更高 revision 前向修复；不使用破坏性 downgrade。

需要收缩模型时采用 expand-and-migrate：

1. 新增替代结构；
2. 通过 ChangePlan dry-run 后追加回填；
3. 发布兼容读写代码；
4. 停止旧字段的新写入，但保留旧字段与历史数据；
5. 将最终物理移除视为单独删除申请，而不是常规迁移的一部分。

### 3. 派生索引策略

Chroma 每次构建使用不可复用的 collection 版本，向量 ID 包含资源、元数据和 embedding 版本。Neo4j 每次构建使用新的 `graph_version`。构建完成后先校验完整性、计数、输入哈希和抽样结果，再追加活动版本记录。

失败版本保留并标记 `NOT_ACTIVE`。运行时继续读取最近一次健康版本；可选索引不可用时降级到 MySQL。资源停用、图环和低覆盖分组只在当前查询或响应中被过滤/忽略，不修改已存事实。

### 4. 文件与容器策略

- 新输出使用唯一名称，保留原文件及其 SHA-256；Git 中的用户改动和未跟踪文件同样受保护。
- 常规停止命令只停止进程/容器并保留持久化卷。
- 测试、演示和实验创建新的命名空间与 `run_id`，结束时封存 Manifest，不销毁环境。
- 容量不足通过告警、扩容、只读归档建议或删除申请处理，不设置自动清理任务。

### 5. 权限与执行策略

- 运行时和 Worker 使用最小账号，只拥有必要的读取、追加和白名单状态更新权限。
- Migrator 只拥有 expand-only DDL 权限，不拥有数据删除、清空或对象移除权限。
- Agent/LLM 只能调用类型化应用端口；不能访问数据库驱动、文件系统删除、Shell、Docker 或自由 SQL/Cypher。
- 写操作均由不可变 ChangePlan 驱动，先进行只读 dry-run。计划必须声明精确环境、目标、输入哈希、预计新增/更新/删除数和影响上限；删除数或覆盖数不是零时拒绝 apply。

### 6. 失败恢复策略

- 代码缺陷通过新修复提交或显式 revert 提交处理，不强制重置工作区。
- 数据或事件错误通过追加补偿事实和新投影版本处理。
- Outbox 使用幂等键重放；超限后保留事件并追加 `DEAD` 状态。
- 迁移失败用新 revision 修复；备份只恢复到新的命名空间，不覆盖源环境。
- 索引失败保留现场，创建新版本重建；活动健康版本继续服务。
- 恢复验收必须证明受保护对象数量未减少，原事实仍可查询，所有影响均在计划上限内。

## 约束如何支持低耦合与高内聚

零删除不是散落在业务代码中的条件分支，而是由边界集中执行：

- 领域模块只表达追加事实、状态转换和补偿语义，保持业务内聚；
- Repository 端口定义可用操作，不向领域层暴露删除能力；
- MySQL、Chroma、Neo4j 和文件适配器分别实现版本与幂等约束，彼此可替换和降级；
- Orchestrator/Agent 产生意图和证据，不直接执行基础设施写入；
- ChangePlan 执行器统一负责环境核验、dry-run、影响上限和审计回执。

因此，安全策略不会迫使 Catalog、Profile、Recommendation、Feedback 等领域模块互相查询或修改内部表，也不会让 MySQL 事实层依赖某个可选索引。

## 后果

### 正面后果

- 保留完整论文实验、推荐解释、画像变化和 Agent 协作证据链。
- 失败可诊断，旧健康版本可继续服务，降级路径明确。
- 避免环境串用、误清理、级联破坏和 LLM 越权。
- 通过版本命名空间、端口和 ChangePlan 降低基础设施耦合。
- 测试可验证幂等、重放和历史时点行为，而不是依赖“重置后成功”。

### 成本与限制

- 存储量持续增长，需要容量监控、配额预测和长期归档方案。
- 查询需要处理当前有效版本、失效状态和活动指针，模型更复杂。
- Fixture、测试用户和实验 run 数量增长，需要清晰命名与 Manifest。
- 物理数据擦除需求不能由普通业务接口立即完成，必须走独立审批和可验证流程。
- 前向迁移要求更严格的兼容窗口和契约测试。

这些成本被接受，因为原型的可审计性、论文可复现性和用户资产安全优先于开发环境的短期整洁。

## 已考虑但拒绝的方案

### 方案 A：仅依赖备份，允许日常删除

拒绝。备份可能不完整或不可恢复，且无法避免误选环境、引用断裂和审计链丢失。

### 方案 B：只禁止生产删除，测试环境可重置

拒绝。论文数据和故障证据主要产生于测试、演示和实验环境；重置会损害复现性，也违反用户对“任何数据库数据”的约束。

### 方案 C：软删除后定期物理清理

拒绝自动物理清理。逻辑停用可作为查询语义，但后台清理仍是删除，必须提交独立申请并获得精确批准。

### 方案 D：由 Agent 自主决定清理无用数据

拒绝。不确定模型不能持有破坏性权限；Agent 只能提出结构化建议，由确定性策略和人工授权控制。

### 方案 E：索引原地重建以节省空间

拒绝。原地重建会产生不可服务窗口并丢失对照证据；采用影子版本和活动指针更符合可降级设计。

## 验证与合规

G0 及后续阶段必须建立自动化门禁，至少验证：

1. Repository/适配器公开接口不存在物理删除能力。
2. 迁移和可执行脚本的危险语义被静态扫描拒绝。
3. 应用账号获得危险权限时 readiness 失败。
4. dry-run 不产生文件或数据库变化，且影响估算可复核。
5. 重复 apply 幂等，同名版本不被覆盖。
6. MySQL、Chroma、Neo4j 或 Worker 故障后旧事实和活动版本仍存在。
7. Git 差异不包含未经批准的文件删除。
8. 每次交付回执明确报告文件删除数、数据库删除数和覆盖数，正常值均为零。

## 后续决策

以下事项需要独立 ADR，不得通过修改本 ADR 隐式决定：

- 模块化单体及端口适配器的依赖规则；
- 具体 ChangePlan Schema 的代码生成与签名方式；
- 隐私擦除或法律义务与证据保留冲突时的专项流程；
- 长期只读归档介质、容量预算和保留策略；
- 生产环境的多方审批、凭证托管与灾难恢复方案。

本 ADR 若被替代，替代 ADR 也必须保留历史文件，并取得用户对安全边界变化的明确批准。
